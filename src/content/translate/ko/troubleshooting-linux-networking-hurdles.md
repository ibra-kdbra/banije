## 현대 라우팅의 복잡성

수많은 시행착오가 있었지만, 마침내 필요한 특정 위치를 경유하는 안정적이고 고속인 개발 환경을 구성하는 데 성공했습니다. 이번 작업이 어떻게 시작되었는지 되돌아보니, 현대의 네트워크 라우팅과 보안 계층이 얼마나 복잡할 수 있는지 다시 한번 실감하게 되었습니다.

---

## 1막: 자동화된 다운로드의 실수

목표는 간단했습니다. 내 클라우드 프로필의 일관성을 유지하고, 리전 간 마찰 없이 GCP와 같은 도구를 사용하며, 백그라운드 스트리밍이 원활하게 유지되도록 특정 `<region>` 노드를 통해 트래픽을 라우팅하는 것이었습니다.

시간을 절약하기 위해 VPNBook의 무료 구성 프로필을 사용하기로 했습니다. 터미널을 열고 빠르게 자동화된 다운로드를 시도했습니다:

```bash
mkdir -p ~/vpnbook && cd ~/vpnbook
curl -O https://www.vpnbook.com/free-openvpn-account/VPNBook.com-OpenVPN-EuroServers.zip
```

엔터를 누르고 전송이 완료되기를 기다린 뒤 `unzip`을 실행했습니다.

:::caution[문제 발생]
터미널에서 치명적인 오류가 발생했습니다: `End-of-central-directory signature not found`. 아카이브 파일을 전혀 읽을 수 없는 상태였습니다.
:::

:::note[교훈]
많은 공용 인프라 제공업체가 안티 봇 검증 계층 뒤에서 자산을 보호하고 있다는 사실을 간과했습니다. 원시 `curl` 명령으로 zip 파일에 직접 접근하자, 호스트는 이 자동화된 요청을 감지하고 실제 zip 아카이브 대신 HTML 오류 페이지를 반환한 것입니다.
:::

:::tip[해결책]
자동화 방식을 포기하고, Firefox를 열어 웹사이트의 안티 봇 검증 페이지를 수동으로 통과한 뒤 브라우저를 통해 구성 파일을 직접 다운로드했습니다.
:::

## 2막: 터널 연결 성공과 누락된 DNS 링크

`~/vpnbook`에 압축 해제된 `.ovpn` 파일들을 배치한 후, 자격 증명을 매번 수동으로 입력하지 않도록 로컬 `auth.txt` 파일을 생성했습니다. 스트림 에디터 명령을 사용하여 프로필에 자격 증명 경로를 추가했습니다:

```bash
sed -i 's/auth-user-pass/auth-user-pass auth.txt/g' *.ovpn
```

포트 25000번의 UDP 프로필을 선택하고 root 권한으로 초기화했습니다:

```bash
sudo openvpn --config vpnbook-de20-udp25000.ovpn
```

터미널 로그가 지나가고 성공 확인 메시지가 출력되었습니다: `Initialization Sequence Completed`.

:::caution[문제 발생]
터널은 활성화되었지만 인터넷 연결이 완전히 작동하지 않았습니다. 웹 페이지는 타임아웃되었고, GCP나 AWS는 로드되지 않았으며, 터미널 도구들도 외부 저장소에 접근할 수 없었습니다.
:::

:::note[교훈]
로그 출력을 더 면밀히 검토한 결과, 연결 시퀀스가 끝나기 직전에 특정 경고를 발견했습니다:
`Failed to set DNS configuration: Could not activate remote peer 'org.freedesktop.resolve1': unknown unit`.

OpenVPN은 원격 노드까지의 네트워크 경로를 설정했지만, 운영체제가 `systemd-resolved`를 사용하여 도메인 이름 변환을 처리할 것으로 기대하고 있었습니다. EndeavourOS는 기본적으로 이 서비스가 비활성화되어 있기 때문에, 내 머신은 네트워크 터널 내부에 안전하게 진입했음에도 불구하고 텍스트 도메인 URL을 숫자 IP 주소로 매핑할 수 없었던 것입니다.
:::

:::tip[해결책]
별도의 터미널 창을 열고 필요한 D-Bus 링크를 초기화하기 위해 네이티브 시스템 데몬을 활성화했습니다:

```bash
sudo systemctl enable --now systemd-resolved
```

서비스가 시작되자마자 DNS 파이프라인이 깔끔하게 해결되었습니다. OpenVPN은 올바른 공용 네임서버를 할당했고, 브라우저는 정상적으로 페이지를 로드하기 시작했으며, 지리적 위치 확인을 통해 외부 연결이 성공했음을 확인했습니다.
:::

## 3막: 속도 병목 현상과 실패 루프

터미널 연결이 작동하자, 시스템 부팅 시 자동으로 실행되도록 자동화하고 싶었습니다. `vpn-failover.service`라는 간단한 systemd 백그라운드 서비스 파일과 기본적인 bash 래퍼 스크립트를 만들었습니다. 구성 프로필을 계층 구조로 정리하여 `udp25000`을 기본 링크로, `udp53`을 보조로, `tcp443`을 마지막 수단으로 설정했습니다.

:::caution[문제 발생]
Failover 스크립트는 잘 작동했지만, 실제 네트워크 성능이 극도로 저하되었습니다. 대역폭이 너무 제한적이어서 기본적인 문서 페이지조차 로드하기 힘들었고, 실시간 코드 도구들은 계속해서 연결이 끊겼습니다.
:::

:::note[깨달음]
근본적으로 과부하 상태인 리소스를 최적화하려던 것이었습니다. 무료 공용 VPN 서버는 전 세계 수천 명의 사용자가 대용량 다운로드 및 자동화된 스크래핑을 위해 공유합니다. 하드웨어 수준에서 이미 포화 상태인 원격 서버 인터페이스를 로컬 스크립트 최적화만으로 해결할 수는 없는 노릇이었습니다.
:::

## 4막: 엄격한 예산 내에서의 대안 평가

사용 불가능한 공용 속도에 직면하여 상용 대안을 검토했고, 특히 월 $2.50의 전용 프라이빗 프록시를 고려했습니다. 이를 통해 개발 도구에 가벼운 애플리케이션 수준의 터널을 제공받길 기대했습니다.

결정하기 전, 두 가지 주요 제약 사항이 있음을 깨달았습니다.

1. **ASN 평판 차단:** 대부분의 저렴한 프라이빗 프록시는 상용 데이터 센터가 소유한 IP 대역에 할당됩니다. 최신 AI 방화벽은 이러한 ASN(Autonomous System Numbers)을 능동적으로 스캔합니다. GCP, AWS 또는 claude와 같은 플랫폼은 일반 가정용 ISP가 아닌 상용 서버 랙에서 들어오는 트래픽을 감지하면 봇으로 간주하여 지속적인 CAPTCHA 챌린지나 완전한 접근 차단을 실행합니다.

2. **예산 한도:** 카드 잔액을 확인하니 정확히 `$7.75`라는 엄격한 한도가 있었습니다. 이는 일반적으로 한 달 이용료로 `$10`에서 `$15`를 선결제해야 하는 주요 상용 VPN 제공업체들을 완전히 배제하게 만들었습니다.

## 5막: 예산 친화적인 커스텀 플랜 구현

IP 평판, 안정적인 접근성, 엄격한 재정 한도 사이에서 절충점을 찾기 위해 Windscribe의 "Build-A-Plan" 티어를 선택했습니다. 이 서비스는 $3의 최소 결제 금액 내에서 사용자당 각 $1로 특정 서버 위치를 개별적으로 구매할 수 있었습니다.

기본 구성을 다음과 같이 조합했습니다:

* 첫 번째 필요한 `<region>` 노드에 대한 프리미엄 서버 접근: $1.00
* 두 번째 필요한 `<region>` 노드에 대한 프리미엄 서버 접근: $1.00
* 무제한 데이터 및 보안 프로필 업그레이드: $1.00
* **총 비용: $3.00**

이 구성은 예산 범위 내에서 안정적으로 유지되었고, 카드에 $4.75의 잔액을 남기면서도 상용 수준의 라우팅 회선에 제한 없는 접근을 가능하게 했습니다.

## 6막: Arch 패키지 충돌 해결

관리를 간소화하기 위해, 원시 구성 파일을 수동으로 관리하는 대신 Arch User Repository에서 공식 GUI 데스크톱 애플리케이션을 설치하기로 했습니다:

```bash
yay -S windscribe-v2-bin
```

시스템이 에셋을 컴파일했지만, 최종 설치 단계에서 Pacman이 명확한 의존성 오류와 함께 트랜잭션을 차단했습니다:
`error: unresolvable package conflicts detected (windscribe-v2-bin and python-windscribe-git are in conflict)`.

:::tip[최종 해결책]
시스템에 남아 있던 이전 타사 패키지가 동일한 디렉토리 경로에 대한 소유권을 주장하고 있었습니다. 이전 의존성을 제거하는 간단한 명령을 실행하고, 설치 프로그램을 재실행하여 캐시된 빌드 파일에서 가져온 다음 백그라운드 관리 데몬을 시작했습니다:

```bash
sudo pacman -R python-windscribe-git
yay -S windscribe-v2-bin
sudo systemctl enable --now windscribe-helper
```

설치가 깔끔하게 마무리되었습니다.
:::

## 최종 워크스페이스 상태

공식 애플리케이션에 로그인하자 원시 터미널 스크립트보다 훨씬 구조화된 설정이 가능해졌습니다:

* **프로토콜 최적화:** 연결 환경 설정에서 드라이버를 OpenVPN에서 WireGuard로 전환했습니다. WireGuard는 패킷을 사용자 공간 전환을 통해 처리하지 않고 Linux 커널 공간 내에서 직접 작동하기 때문에, 연결 속도가 즉시 내 가정용 대역폭 용량만큼 충족되었습니다.
* **분할 터널링:** 애플리케이션 수준의 라우팅을 활성화하여 Firefox와 특정 IDE 프로세스만 프리미엄 `<region>` 노드를 통해 라우팅되도록 설정했습니다. 이를 통해 클라우드 서비스에서 내 신원을 완전히 일관되게 유지하면서도, 핵심 시스템 업데이트, 로컬 컨테이너 및 일반 유틸리티는 기존 가정용 네트워크 연결로 실행되도록 했습니다.

이 과정에서 몇 가지 전형적인 Linux 네트워킹 함정을 수정해야 했지만, 이제 환경은 안정되었고 예산은 유지되며 워크스페이스는 완벽하게 작동하고 있습니다.
